# Прогресс просмотра на ТВ: синхронизация с аккаунтом

**Статус:** реализовано 15.09.2026, этапы 0–5. Живая проверка на боксе с
реальным аккаунтом не проводилась.

План переноса на `anion-tv` того, что уже сделано в вебе и на бэке. Как это
устроено там — [anion/docs/watch-progress-sync.md](../../anion/docs/watch-progress-sync.md):
на сервере одна строка `watch_progress` на пользователя+аниме, внутри номера
просмотренных серий; эндпоинты `GET/PUT /watch-progress/:animeId` и
`POST /watch-progress/sync`; счётчик закладки сервер двигает сам.

## Как сейчас на ТВ

- **Room — источник правды.** `watch_progress` хранит строку на серию
  `(source, animeId, episode)` с позицией и флагом `finished` (досмотр на 90%).
  Поля `updatedAt`/`syncedAt` с CAS в `markSynced` — готовая очередь отправки.
- **На сайт прогресс уходит только косвенно.** `PlaybackProgressRecorder.flush`
  на досмотре зовёт `bookmarks.advanceWatched`, закладка становится dirty и
  уходит `PUT /bookmarks` со счётчиком. `begin` зовёт `ensureWatching` и
  создаёт закладку «Смотрю» на любой начатый тайтл.
- **С сайта на ТВ прогресс не приезжает.** `DetailsViewModel.watchedEpisodes`
  собирается только из локальных `finished`.
- **Ключи.** AniLibria-озвучка Kodik-тайтла пишется под `(KODIK, yumiId)`:
  `AnionNavHost` передаёт в плеер `route.source`/`route.animeId` карточки, так
  что такие серии синкаются. Тайтлы, открытые из ряда AniLibria, живут под
  `(ANILIBRIA, alias)` — у сервера такого ключа нет, они остаются локальными,
  как и решено в PLAN §Э5.
- **Баг.** В `HttpBookmarkRemote.request` нет ветки `DELETE`; билдер OkHttp по
  умолчанию шлёт `GET`, и удалённая на ТВ закладка на сайте остаётся.

## Принятые решения

| Вопрос | Решение |
| --- | --- |
| Когда серия просмотрена для сервера | На 90% длительности — как сейчас (`ProgressPolicy`) |
| Автозакладка «Смотрю» при старте | Убрать |
| Позиция внутри серии | Остаётся локальной в Room — как позиция в IndexedDB на вебе |
| Набор просмотренных серий | Истина — сервер; локальные `finished` — очередь отправки и мгновенный показ |
| Показ серий с сайта без сети | Вне объёма: набор с сервера живёт в памяти экрана |
| «Продолжить смотреть» с учётом сайта | Вне объёма |
| Починка `DELETE` закладок | В объёме |

## Этап 0. Хотфикс: счётчик закладки не должен уменьшать прогресс

**Проблема.** Правило на бэке «счётчик закладки меньше `max_episode` →
перезаписать набор» срабатывает на любой устаревший счётчик, а не только на
осознанную правку:

- ТВ всегда шлёт `watchedEpisodes` и в `PUT`, и в `POST /bookmarks`, а
  `DetailsViewModel.setBookmark` делает `pushDirty()` без `pull`. На сайте
  просмотрено 8 серий, на ТВ поменяли статус при локальном счётчике 3 → набор
  на сервере становится `{1,2,3}`.
- `CreateBookmark` проходит через то же правило.
- Веб тоже: `bookmark-tile.onSaveEdit` отправляет `watchedEpisodes` из
  загруженной закладки даже при смене одного статуса.
- Сама колонка `bookmarks.watched_episodes` пишется как `= N`, то есть тоже
  откатывается назад.

`anion-dl` закладки не трогает — пишут только веб и ТВ.

**Бэк (`anion-go`):**

- `WatchProgressRepository.ApplyBookmarkCounter` получает `allowDecrease bool`.
  Без флага — только объединение с `{1..N}` и `max_episode = GREATEST(max, N)`.
  С флагом — нынешнее поведение с перезаписью при `N < max`.
- `dto.UpdateBookmarkPayload` — новое поле `ReplaceProgress bool
  json:"replaceProgress"`. Уменьшение разрешено, только когда оно `true` и
  `WatchedEpisodes != nil`.
- `CreateBookmark` вызывает применение счётчика всегда без уменьшения.
- `BookmarksRepository.UpdateBookmark`: без флага
  `watched_episodes = GREATEST(watched_episodes, N)`, с флагом — `= N`.
- Тесты: сервис закладок (с флагом и без, create, update); SQL прогнать на
  одноразовом Postgres, как при первой реализации.

**Веб (`anion`):**

- Плитка закладки отправляет `watchedEpisodes`, только если число реально
  изменили, и добавляет `replaceProgress: true`, если стало меньше исходного.
- Поле в `UpdateBookmarkPayload` и в `BookmarksService.updateBookmark`.

**Выкатка.** Gin игнорирует неизвестные поля, так что порядок не ломает сборку,
но между выкатками либо сохраняется старый риск (веб первым), либо веб-редактор
временно не может уменьшить счётчик (бэк первым). Выкатывать вместе, бэк на
пару минут раньше.

## Этап 1. ТВ: сетевой слой прогресса (`core-data`)

- **Общий HTTP-хелпер.** Вынести приватный `request()` из `HttpBookmarkRemote`
  в `internal` класс рядом (заголовки `X-Anion-Client`, данные клиента,
  `Cookie: X-Session-ID`, разбор `ApiException`). Им пользуются оба remote.
  При переносе:
  - добавить ветку `"DELETE" -> builder.delete()` — это и есть починка из
    объёма;
  - `204` без тела возвращать как `null`: сейчас пустая строка ушла бы в
    `decodeFromString` и упала.
- **`WatchProgressRemote`** — интерфейс и HTTP-реализация:
  - `get(sessionId, animeId): RemoteWatchProgress?` — `GET /watch-progress/:animeId`,
    `null` на `204`;
  - `sync(sessionId, items): List<RemoteWatchProgress>` —
    `POST /watch-progress/sync`. Отдельный `PUT` на одно аниме не нужен:
    батч из одного элемента покрывает этот случай.
- **DTO** зеркалит `models.WatchProgress`: `animeId: Int`,
  `episodes: List<Int>`, `maxEpisode: Int`, `updatedAt: String`. По конвенции
  AGENT.md форма фиксируется фикстурой — реальный ответ снять с сессией в
  `core-data/src/test/resources/fixtures`.
- **Лимиты сервера** держать на клиенте: не больше 200 элементов в `sync`, не
  больше 5000 номеров на аниме, номера 1..10000.
- **Тесты** (JVM, MockWebServer, по образцу `AccountLoginErrorsTest`): метод,
  путь, кука и тело `sync`; `204` → `null`; `delete` уходит именно `DELETE`.

## Этап 2. ТВ: отправка досмотренных серий

- **Шаг `pushProgress()` в `DefaultBookmarkSync`.** Мьютекс, `SyncState` и все
  точки вызова (`syncIfStale`, дебаунс рекордера) уже есть — отдельный класс
  синка сейчас был бы дублированием. Логика:
  `pendingSync()` → только `KODIK` и `finished` → группировка по `animeId` →
  пачки по 200 → `remote.sync` → CAS `progress.markSynced(row)` на каждую
  отправленную строку. Сбой — строки остаются pending: очередь здесь сама Room,
  отдельной, как на вебе, не нужно.
- **Порядок в `syncNow`**: pull закладок → `pushProgress()` → `pushDirty()`.
  Прогресс раньше закладок, потому что `CreateBookmark` берёт счётчик из
  прогресса.
- **Выборка.** `pendingSync()` возвращает и тикающие недосмотренные строки,
  которые на сервер не идут никогда. Добавить в DAO запрос только по
  `finished = 1` — это не меняет схему, миграция не нужна.
- **Убрать косвенный путь:**
  - блок в `pushDirty`, который помечал прогресс синхронизированным по
    счётчику закладки;
  - `bookmarks.advanceWatched` из `PlaybackProgressRecorder.flush`;
  - `ensureWatching` (и `syncNow`, стоявший перед ним ради защиты dirty-счётчика)
    из `begin`; после досмотра по-прежнему `scheduleSync()` с дебаунсом 12 с.
- **Пейлоады закладок** больше не содержат `watchedEpisodes` ни в `payload()`,
  ни в `createPayload()`: счётчик выводит сервер. После Этапа 0 это не
  обязательно для безопасности, но ТВ счётчик больше не знает лучше сервера.

## Этап 3. ТВ: разовый перенос локальной истории

- Строки, записанные без входа в аккаунт, имеют `syncedAt = null` и уйдут
  обычным `pushProgress()` сразу после входа — для этого ничего делать не нужно.
- Строки, отправленные старым путём, на сервере отражены только счётчиком: бэкфилл
  превратил его в `{1..N}`. Если закладку удалили до бэкфилла, серий на
  сервере нет вовсе. Поэтому один раз после обновления отправить **все**
  `finished`-строки `KODIK` независимо от `syncedAt`. Слияние на сервере —
  объединение, повтор безопасен.
- Флаг `watch_progress_migrated_v1` в `SharedPreferences` рядом с сессией,
  ставится только после успеха. Флаг общий, а не на аккаунт — по той же
  причине, что на вебе.

## Этап 4. ТВ: серии с сайта на экране деталей

- **Источник.** Небольшой репозиторий над `WatchProgressRemote` и
  `SessionStore`: `remoteWatched(animeId): Set<Int>?`, `null` без сессии, для
  не-Kodik или при ошибке.
- **`DetailsViewModel`.** В `fetch()` для `KODIK` параллельно с деталями
  запросить набор с сервера. Хранить отдельно от локального, объединение
  считать в одном месте: `watchedEpisodes = локальные finished ∪ серверный набор`.
  Правило объединения вынести в чистую функцию и покрыть JVM-тестом.
- **Свежесть** — по правилам AGENT.md: тот же TTL и `keepVisible`. Ошибка сети
  не стирает показанный набор. Досмотр на самом ТВ появляется мгновенно через
  Flow из Room; отметки с сайта — при повторном открытии или после TTL в
  5 минут.
- **Выход из аккаунта.** Подписаться на `account.signedIn`; при `false`
  серверный набор сбрасывается, локальные `finished` остаются.
- **UI не меняется:** `EpisodeCard` уже прячет полоску частичного просмотра у
  отмеченной серии, а главная кнопка ведёт на первую непросмотренную — теперь с
  учётом сайта.
- **«Продолжить серию N»** не предлагать для серии из объединённого набора. Это
  то же правило «отметка важнее позиции», что уже действует в `EpisodeCard`.

## Этап 5. Документация

- AGENT.md, «Грабли»: у билдера OkHttp метод по умолчанию `GET`, и без явной
  ветки `DELETE` запрос молча уходит не тем методом; `204` приходит без тела;
  счётчик закладки больше не несёт прогресс.
- AGENT.md, «Состояние», и PLAN.md §Э5: прогресс уходит отдельным эндпоинтом,
  закладки не создаются автоматически.

## Краевые случаи

| Ситуация | Поведение |
| --- | --- |
| Досмотр на ТВ без сети | Строка pending в Room, уйдёт при следующем `syncNow` |
| Пересмотр досмотренной серии | `finished` липкий, `updatedAt` растёт, строка снова pending; повторная отправка безопасна |
| Сайт и ТВ одновременно | Объединение на сервере, потерь нет |
| Серия отмечена на сайте, на ТВ досмотрена наполовину | Отметка есть, полоски нет, «продолжить» её не предлагает |
| Тайтл из ряда AniLibria | Только локально, как и раньше |
| Выход из аккаунта | Серверные отметки с экрана уходят, локальные остаются |
| Другой аккаунт на том же боксе | Неотправленные строки прошлого аккаунта уйдут новому: Room не разделён по пользователям. Для личного приложения приемлемо; разделение — вне объёма |
| Лимиты сервера | Пачки по 200 аниме, до 5000 номеров |
| `429` / `5xx` | Строки остаются pending до следующего синка |
| Протухшая сессия | Ошибка в `SyncState` — как сейчас у закладок |
| Счётчик на плитке закладки ТВ | Сервер двигает его сам; цифра на ТВ догонит при следующем pull |

## Решено по ходу

- **Авто-«Просмотрено»** остаётся только для уже существующей закладки:
  `BookmarkRepository.completeIfLast` меняет статус при досмотре последней серии
  и новых закладок не создаёт.
- **Отправка прогресса не держит закладки.** Шаг `pushProgress()` идёт раньше
  `pushDirty()`, но его ошибка всплывает только после отправки закладок: иначе,
  например, до выкатки бэка ТВ перестал бы синкать и их.
- **Правило объединения отметок** вынесено в `EpisodeMarksPolicy` и покрыто
  JVM-тестами; `DetailsViewModel` хранит локальный и серверный наборы раздельно
  и не пускает в карточку ответ по тайтлу, который уже закрыли.

## Порядок и проверка

Этап 0 идёт первым и выкатывается отдельно — он закрывает риск на проде
независимо от ТВ. Дальше 1 → 2 → 3; этап 4 требует только этапа 1 и может
идти параллельно со 2–3.

- **Бэк:** `go test ./...`, `make lint`, SQL на одноразовом Postgres.
- **Веб:** `ng test`, сборка.
- **ТВ:** `./gradlew :core-data:test` и `./gradlew build -x lint`. Живые
  критерии требуют бокса или ТВ-эмулятора и реального аккаунта: серия,
  досмотренная на ТВ, отмечена на сайте (критерий Э5), и наоборот — серия,
  отмеченная на сайте, видна в карточке на ТВ.
